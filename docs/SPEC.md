# SPEC.md — プチ麻雀（pujan）仕様書

ゲームルール・ローグライト・画面・API・データ構造の正本。ルールに関わる変更の前に該当する節を読み、変更したらこの文書も直す。

ルールとローグライトの数値は、プロトタイプ [`docs/prototype/puchi-mahjong.html`](prototype/puchi-mahjong.html) で検証して確定したもの。迷ったらプロトタイプの挙動を正とし、食い違いを見つけたらこの文書かエンジンのどちらが正しいかを利用者に確かめる。

## 1. プロジェクト概要

### 1.1. コンセプト

手牌を 5 枚（雀頭 2 ＋面子 3）に縮めた麻雀を、Balatro 型のローグライトとして遊ぶ Web ゲーム。

- スマートフォンの縦持ちで、牌を大きく表示できる
- 1 局が 30 秒〜1 分と短く、スキマ時間で遊べる
- 麻雀を知らない人にもルールが伝わりやすい

着想は「白發中が 3 枚あれば大三元と言い張れる」こと。役を 5 枚に縮めた「プチ役」の名前の格好よさと、「それは無理がある」という笑いの両方をテーマにする。

### 1.2. 配信と名前

- 名前: プチ麻雀。リポジトリ・パッケージ名は `pujan`
- kan-game.app のゲームの 1 つとして Web（PWA）で配信する。本番 `https://pujan.kan-game.app`、開発 `https://pujan-dev.kan-game.app`（予定）
- ID・名前・退会は kan-game.app の ID 基盤（kan/game）と共通（§5.1）

### 1.3. モード

| モード | 状態 | 内容 |
|---|---|---|
| ローグライト | 最初に作る | ソロ。東南西北の 4 場を勝ち抜く（§4） |
| AI 対戦 | 後で作る | CPU と 1 対 1（§3.7） |
| ネット対戦 | 後で作る | プレイヤー同士の 1 対 1（§3.7） |

3 つとも同じエンジン（`engine/`）の上に作る。

## 2. 画面と世界観

### 2.1. 世界観

麻雀卓の緑のラシャと象牙色の牌。色と書体はプロトタイプの `:root` を基準にする（`frontend/src/theme.css` に写してある）。

- 牌の地は象牙色（CSS で描く）。面の絵は公開素材 [FluffyStuff/riichi-mahjong-tiles](https://github.com/FluffyStuff/riichi-mahjong-tiles)（CC0）の SVG を使う（`frontend/public/tiles/`。出典とライセンスは同じフォルダの `README.md`）。プロトタイプは CSS と文字で描いていた
- 萬子・筒子・索子・字牌は素材の絵柄のまま。白は無地（絵柄のない牌）
- 赤の 5 は素材の赤牌の絵を使う。朱塗りで 5 以外の牌が赤牌になったときは、素材に赤版がないので左上に赤い印を付ける
- 金牌は金色の地にする。万能牌は面全体を専用の絵柄（薄紫の地に金の星）にし、元の牌を右下に小さく添える
- 和了の画面では、万能牌を当てはめた後の牌で描き、右下に小さな星を付ける（元の牌は出さない）。局の画面の「和了れます」の表示では、万能牌を何の牌として扱うかを添える

### 2.2. 局の画面（縦持ち 1 画面）

上から次の順に並べる。プロトタイプの最終版（UI を確定した版）と同じ。

1. **ヘッダー**: タイトル、役（役と遊び方をすぐ開く）、メニュー
2. **状況の帯**: 4 局の並び（親とボスの印つき）、局名と本場、巡（残り 3 巡以下で金、最終巡で赤）、点数／目標と進捗バー
3. **情報**: リーチ中の印、ボスの縛り、ドラ表示→ドラ（または万能牌）、自風（いずれも牌の絵で大きく）
4. **持ち物**: 祝儀、「持ち物」のボタン（お守りの数、設備の数、牌山を改造したかの印。タップで持ち物一覧）、消耗品（タップで使う。染め粉はタップすると残す色のボタンが並び、色を選んで使う）
5. **河**: 1 行の細い帯。新しい捨て牌が右端。タップで全部を広げる
6. **中央**: その時に要る情報だけ。和了れるときは役と点数を金の枠で大きく。それ以外は待ち牌と残り枚数、操作のヒント
7. **保留枠とネクスト**: 保留枠（左）と、次にツモる牌（右。左が次、`←` で順番を示す）
8. **手牌**: 手牌 4 枚とツモ牌
9. **操作ボタン**: その場でできるものだけ出す（配牌の引き直し、保留、リーチ、和了、最終巡の延長）

操作:

- 牌をタップで選択、選んだ牌をもう一度タップで捨てる（「捨てる」ボタンは置かない）
- 空いた保留枠をタップすると、選んだ牌を保留する
- 和了れるときは、和了に使う 5 枚（三対子は 6 枚）を金の枠で示す

### 2.3. その他の画面

- 和了: 和了牌、役と翻、点数の内訳（親・リーチ後の巡・本場・役レベルなど）、祝儀。親の和了では「和了やめ」「連荘する」
- 流局: 聴牌料・罰符・リーチ棒の没収
- ランの準備: 雀士と段位を選ぶ（まだ選べないものは解禁の条件を見せる）。選んだ条件の目標点・保留・ネクスト・巡・祝儀・持ち物を示す。前のランで選んだものをはじめから選んでおく
- 場の開始: 雀士・段位、目標点、親番の局、オーラスのボス
- 場の突破: 局ごとの記録と祝儀の内訳
- ショップ: 品物 3 つ（雀聖は 2 つ）、品替え、持っているお守りと消耗品の売却。持ち物一覧も開ける（閉じるとショップに戻る）
- 持ち物一覧: お守り・設備・役の巻物のレベル・牌山。牌山は 34 種の牌に、山にある枚数・赤・金を添えて並べ、牌の改造で変わった牌を金の枠で示す（牌の改造の対象選びでも、変わった牌を金の枠で示す）
- 牌の改造の対象選び: 34 種の牌と、山にある枚数・赤・金
- ラン終了・全場クリア（新しく解禁されたもの、ランキングへの記録の様子、感想を送る、メニュー）。この画面はヘッダーを覆うので、メニューはこの画面のボタンから開く。メニューを閉じるとこの画面に戻る
- メニュー（TAKO-SEN に倣う）: ランキングの名前、kan-game.app のアカウント（ポータルへのリンク）、今週のランキング、遊び方（チュートリアル）、役と遊び方、持ち物、新しいランを始める（ランの準備へ。今のランをやめることはそこで知らせる）、感想を送る、プチ麻雀について（β版の説明、集める情報、素材と書体のライセンス、版）
- 感想を送る: 本文（1,000 字まで）と、一緒に送るもの（雀士・段位・進み具合・版）を見せてから送る。送れた感想は端末（localStorage）に 20 件まで残し、画面の下に新しい順で見せる（サーバーからは読まない）
- β の間は、ヘッダーのタイトルに「β」の印を付ける
- 役と遊び方: タブで、遊び方・ボーナスの翻・1〜2翻・3翻以上・役満・点数表・アイテムに分ける。組み合わせの役は牌の絵で例を示す（例の手は `frontend/src/lib/help.ts`。その役になることをテストで確かめる）
- チュートリアル（TAKO-SEN に倣う）: 山の並びを決めた練習の局で、捨てる・保留する・ネクストを見る・和了るを実際に操作してもらい、言われた操作ができたら次へ進む。次に押すところ（牌・空き枠・ボタン）は、文字の指示に加えて金の輪と指のマークで光らせる（動きを減らす設定では動かない輪だけ）。そのあとランの流れ（場・目標点・親・ボス・ショップ・祝儀）を説明する。初めて開いたときは見るかどうかを聞く（`frontend/src/lib/tutorial.ts`）
- ランキング（§5.4）

ルール設定の画面は置かない（プロトタイプの設定画面はルールの調整用だった）。ルールは雀士と段位だけで決まる（標準・初段で 12巡・保留3枠・ネクスト2枚・赤牌あり・海底あり。§4.6）。

## 3. ゲームルール

### 3.1. 牌と山

- 通常の 136 枚（34 種×4 枚）。ローグライトでは牌の改造で種類ごとの枚数が 0〜5 枚に変わる（§4.5）
- 赤牌: 各色の 5 に 1 枚ずつ（設定で外せる）
- 金牌: 牌の改造「金箔」で作る。和了に使うと 1 枚につき祝儀＋2（和了の画面で、祝儀のうち金牌の分を分けて示す）
- 局ごとに山を作り直す（和了ったあとも、流局のあとも）

### 3.2. 局の流れ

- 配牌は 4 枚。1 巡に 1 枚ツモり、手牌・ツモ牌・保留牌から 5 枚で和了判定する
- 1 局は 12 巡（設備・ボス・段位・延長で増減する。§4.4）。和了るか、最後の巡を終えると局が終わる。**1 局で和了れるのは 1 回**
- 打牌: 手牌・ツモ牌・保留牌のどれでも捨てられる。保留牌を捨てると、空いた枠にツモ牌が入る
- **保留枠**: 3 枠。牌を置いておけ、和了判定に使える。手牌と保留枠の入れ替えはない（どちらも和了判定に使うため）
- **ネクスト**: 次にツモる 2 枚が見える
- **配牌の引き直し**: 1 局に 1 回、1 巡目でまだ何も捨てても保留してもいないときだけ。手牌とツモ牌を山に戻して配り直す
- **聴牌料**: 流局時、最後の打牌のあとに聴牌していれば 200 点
- **リーチ**: 牌を選び、それを捨てると聴牌になるときに宣言できる。リーチ棒 100 点（流局すると没収、和了ると戻る。設備「平常心」があれば流局でも戻る）。以後は手牌も保留も固定でツモ切りのみ、ネクストが隠れる。和了で 1 翻（平常心で 2 翻）と裏ドラ。一発はなく、代わりに宣言から和了までの巡数×100 点
- **ドラ**: ドラ表示の次の牌が 1 枚 1 翻。設備で万能牌に変えられる（§4.4）
- **海底**: 最終巡のツモで和了ると 1 翻（設定で外せる）。延長札で巡を延ばすと、延ばした最後の巡に移る
- **親**: 4 局のうち 1 局が親番（場の開始時に分かる）。親の和了は 1.5 倍で、和了後に「連荘（本場が積まれる）」か「和了やめ」を選ぶ。本場は次の和了に 1 本場 100 点。流局すると親は流れる（聴牌でも連荘しない）。親のノーテン流局は罰符 300 点×（本場数＋1）
- **自風**: 親の局は東（場風と重なればダブ東）。それ以外は親の局から逆算し、親の直前が南、その前が西、親の直後が北

不採用にしたもの（再検討するときの参考）:

- 2 枚ツモって 1 枚選ぶ: 和了率は最も上がった（12 巡で 76%）が、麻雀経験者ほど混乱する
- 和了ったあとも 12 巡まで続ける Balatro 式: 安手の連打が最適解になり、麻雀らしくない
- 聴牌連荘: 聴牌が容易なので親番が終わらなくなる
- 一発: ネクストがあるのでリーチがやり得になる

### 3.3. 役

和了形は対子＋面子（順子・刻子）が基本。役がなくても和了れる（役なし 100 点）。

| 役 | 条件 | 翻 |
|---|---|---|
| プチ国士 | 三元牌・風牌・1 牌・9 牌を 1 枚ずつ＋そのどれかの対子 | 1 |
| 断么九 | 么九牌を含まない | 1 |
| 役牌 | 三元牌・場風・自風の対子か刻子＋面子。重なれば加算（親の東はダブ東で 2） | 1〜 |
| 門前 | 保留牌を使わずに和了（役満以外と複合） | 1 |
| 混一色 | 数牌 1 色＋字牌 | 2 |
| プチ三色 | 同じ数字の 3 色の面子＋対子 | 2 |
| プチ一通 | 同色の 5 連（12345 など）。清一色と必ず複合 | 2 |
| プチ小四喜 | 風牌 3 種＋対子（何でも可） | 2 |
| 三対子 | 保留を含めた 6 枚で対子 3 組（門前とは両立しない） | 2 |
| 清一色 | 数牌 1 色のみ | 3 |
| プチ四暗刻 | 刻子＋対子 | 3 |
| プチ小三元 | 白發中＋対子 | 5 |
| 混老頭 | 么九牌のみで刻子を含む | 役満 |
| 字一色 | 字牌のみ | 役満 |
| 緑一色 | 2・3・4・6・8 索と發のみ | 役満 |
| プチ大四喜 | 東南西北＋三元牌 1 枚 | 役満 |
| プチ槓 | 同じ牌 4 枚＋何か 1 枚 | 役満 |
| 天和 | 1 巡目のツモで和了 | 役満 |
| 地和 | 一度も捨てずに 2 巡目で和了（保留は可） | 役満 |
| プチ大三元 | 三元牌の刻子＋残りの三元牌 1 枚ずつ | ダブル役満 |

ボーナスの翻: リーチ 1、海底 1、ドラ 1／枚、赤 1／枚、裏ドラ 1／枚。ボーナスは役に数えない（ボス「1 翻縛り」で効く）。

役満は重なれば倍数を足す（例: プチ大三元＋字一色は 3 倍役満）。147・258・369 は役にならない（お守り「飛び石」で順子になる）。

難しさの目安（配牌 5 枚で完成する確率／保留なし 12 巡での和了率）は、コンセプト資料とエンジンのシミュレーションで確かめる。主なもの: 基本和了 1/1,281・21%、プチ国士 1/2,170・25%、清一色 1/6,249・12%、プチ小三元 1/29,756・2.4%、プチ大三元 1/1,874,652・0.2%。

配牌の確率は「形」の確率で、上位の役（役満など）に吸収される手も数える。基本和了は対子＋順子か刻子、清一色は 1 色の対子＋面子（プチ一通の 5 連は含まない）。配牌の確率はエンジンの数え上げ（`engine/src/sim.ts` の `dealTable`）と一致し、回帰テストにしている。12 巡の和了率は AI の打ち方で変わる（エンジンの AI では、ネクストを使わないときに基本和了 18%・プチ国士 25%・清一色 12%）。

### 3.4. 点数

| 翻 | 名前 | 点数 |
|---|---|---|
| 0（役なし） | — | 100 |
| 1〜4 | — | 200・400・800・1,600（100×2^翻） |
| 5 | 満貫 | 2,000 |
| 6〜7 | 跳満 | 3,000 |
| 8〜10 | 倍満 | 4,000 |
| 11〜12 | 三倍満 | 6,000 |
| 13〜 | 数え役満 | 8,000 |
| 役満 | — | 8,000×倍数 |

お守り「青天井」があると上限がなくなり、翻ごとに倍のまま。

基本点に次の順で掛け合わせる・足す（`engine/src/score.ts`）: 役レベル（×1.5^Lv）→ 安手の美学（役なし×4）→ 親（×1.5、100 点単位に切り上げ）→ リーチ後の巡（＋100／巡）→ 本場（＋100／本場）。

### 3.5. 局の精算

- 和了: 点数を加える
- 流局: 聴牌料（聴牌時）を加え、親のノーテン罰符とリーチ棒を引く

### 3.6. 決定性

山の並びとショップの品揃えはシードから決まる。同じシードと同じ操作列からは必ず同じ結果になる（サーバーでの操作ログの再生による検証のため。§5.3）。乱数は xorshift32（vegtab と同じ）。

全員で同じシードを遊ぶ形（デイリーなど）は設けない。ランはいつもランダムなシードで遊び、競い合いの中心は将来の対戦モード（§3.7）とする。ランキングに載せるランのシードはサーバーが渡す（§5.3）。

### 3.7. 対戦モード（後で作る）

検討済みの方針。作るときに詳細を詰める。

- 1 対 1。1 翻縛り（役なしの最速和了が最適解になるのを防ぐ）
- 鳴きなし（ポンすると残りが単騎待ちになり極端なため）。ロンとツモのみ
- 保留枠は表向きに公開する
- 相手が保留枠に置いた牌でもロンできる（槍槓と同じ扱い。置いた瞬間だけ）。常時ロン可にする案もあり、設定で切り替えて比較する
- AI 対戦の CPU はエンジンを使う。ネット対戦は Durable Objects で部屋を持つ

## 4. ローグライト

### 4.1. ランの流れ

- 東南西北の 4 場を勝ち抜けばクリア。1 場は 4 局
- 場の目標: 東 1,000・南 2,000・西 4,000・北 8,000 点。点数は場ごとにリセット、場風も変わる
- 場の開始時に、親番の局（ランダム）とオーラス（4 局目）のボス（ランダム）を示す
- 局が終わるたびにショップが開く（4 局目のあとは場の判定）
- 4 局の合計が目標に届かなければラン終了。五段からは、オーラスで和了らないと目標に届いていても突破できない（雀聖は目標点の 1/4 以上の和了が要る。§4.6）
- **オーラスの和了の褒美**: オーラスで和了ると、福引きと同じ景品（消耗品・お守り・役の巻物・設備。§4.4「福引き」）から 1 つを、はずれなしでその場でもらう。場ごとに最初の 1 回だけ（親の連荘で何度和了っても 1 回）。福引きのない雀聖でももらう。和了でランが終わる（場で負ける・全場クリア）ときはもらわない。景品の選び方は福引きの当たりと同じ（受け取れない品を除いて重みで選ぶ）で、乱数はランの乱数から引く

目標点に早く届くと残りの局が消化になり緊張感が下がる、という β の感想から足した（GitHub issue #9）。ごほうび（褒美）で最後まで和了を狙わせ、高い段位では突破の条件にもする。挙がった案のうち、和了の回数を目標に入れる案は採らなかった。

### 4.2. ボス（オーラスの縛り）

| ボス | 縛り |
|---|---|
| 保留封印 | 保留枠が使えない |
| 霧 | ネクストが見えない |
| 1 翻縛り | 役なしでは和了れない（ドラ・赤・門前は役に数えない） |
| 早仕舞い | 巡数が 4 少ない |
| 質素倹約 | ドラと赤の翻がつかない |

### 4.3. 祝儀（お金）

点数とは別の通貨。最初は 4。

- 和了: 2＋翻数の半分（最大 6）。役満は 6。金牌 1 枚につき＋2
- 流局時の聴牌: 1
- 場の突破: 3（三段以上は 2。§4.6）＋利子（5 ごとに 1、最大 5）＋目標超過（50% ごとに 1、最大 3）

祝儀とは別に、福引き券（§4.4「福引き」）を場の突破と金牌での和了でもらう。オーラスの和了では、祝儀とは別に景品を 1 つもらう（§4.1）。

### 4.4. アイテム

| 種類 | 枠 | 価格 | 内容 |
|---|---|---|---|
| お守り | 5 | 5（青天井は 8） | 常時効果。売ると祝儀 2 |
| 設備 | — | 8 | 永続の強化 |
| 消耗品 | 2 | 3 | 局の中で 1 回使う。売ると祝儀 1 |
| 牌の改造 | — | 3 | 山の構成を変える。ラン中ずっと残る |
| 役の巻物 | — | 3 | 指定の役を含む和了の点数×1.5（重ねがけ可） |

ショップは 3 品。種類の出やすさはお守り 35%・消耗品 20%・牌の改造 15%・役の巻物 15%・設備 15%（設備を 9 種に増やしたときに、お守りから 5% を移した）。持っているお守りと設備、並んでいる品は重ならない。品替えは祝儀 2。

**福引き**: ショップで、何が当たるか分からない買い物を 1 回だけできる（ショップを開くたびに 1 回。品替えでは戻らない）。段位が雀聖のランにはない（§4.6）。

- 祝儀 2 で回す。福引き券を持っていれば、祝儀の代わりに券を 1 枚使う（券を先に使う）
- はずれは 30%。祝儀で回したときは祝儀 1 が戻る（券で回したときは戻らない）
- 当たりは、消耗品 30・お守り 20・役の巻物 15・設備 5 の重みで種類を選び、その中から 1 つをその場で持ち物に加える。牌の改造は出ない（対象の牌を選ぶ手順が要り、抜き取りが望まない牌に当たる事故も起きるため）
- 受け取れない品は景品から除き、残った種類で重みを配分し直す: 枠がいっぱいのお守り・消耗品、持っているお守り・設備、棚に並んでいるお守り・設備（当たったあとに棚から買うと 2 つ持てるため）、前提の設備を持っていない設備、解禁していない役の巻物とお守り。受け取れる品がどの種類にもなければはずれ
- 福引き券は、場を突破したとき（全場クリアを除く）と、金牌を使って和了ったとき（金牌の枚数によらず 1 枚。北場の 4 局目に子で和了ったときは、あとにショップが開かないので渡さない）にもらう
- 乱数はランの乱数から引く（同じ操作ログから同じ景品になる）

福引きは GitHub issue #12 で足した。値段と景品の割合は、景品の価値の平均（ショップの価格で数えたもの）がショップより少し得になるように決めた。

**延長**（GitHub issue #11）: 延長札を持っていなくても、局の画面で祝儀 5 を払って巡数＋3 にできる。使える場面は延長札と同じ（最終巡のツモのあと、打牌の前。リーチ中も使える）。延長札と合わせて 1 局に 1 回まで。最終巡で延ばせるときは操作ボタンに「延長」を出し、祝儀が足りなければ押せなくする。和了れるときは出さない（延ばすと海底が外れ、海底だけの手では和了れなくなるため）。

延長札（ショップで祝儀 3）は、前もって買い、消耗品の枠も使うので、祝儀で払う延長より安い。どちらも 1 回あたりの値段は、長考（8 で毎局＋2）より高くしてある。雀士の能力（特定の雀士だけ安い など）にはしていない。延長の使われ方はプレイの集計（祝儀で延ばした回数と、延長札を使った回数）で見る。

**牌の改造**: 朱塗り（選んだ牌を全部赤牌に）、金箔（選んだ牌の 2 枚を金牌に）、抜き取り（その牌を山から全部抜く）、写し（その牌を 5 枚に）。1 枚の牌は赤と金を兼ねない（朱塗りは金牌でない牌を赤牌に、金箔は赤牌でない牌を金牌にする）。写しのあとに朱塗りをすると赤牌は 5 枚になり、朱塗りのあとに写しをすると増えた 1 枚は赤牌にならない。

朱塗り・金箔は、2026-10 までは「2 枚を赤牌に」「1 枚を金牌に」だった。1 局で目にする牌は 16 枚ほどなので、改造した牌を 1 局で引ける見込みが 1〜2 割しかなく、効果が体感しにくかったため強めた。

### 4.5. ビルドの軸

アイテムは次の軸のどれかを伸ばすように作る。新しいアイテムもこの軸に沿わせ、軸を増やすときは仕様を更新する。

- 速攻: 保留・ネクストで安く早く和了る
- 門前・リーチ: 保留を使わず、ネクストを捨てて翻を稼ぐ
- 役満: 牌山の改造と万能牌で一発を狙う
- 親番: 連荘で局数を稼ぐ
- 赤・ドラ: ボーナスの翻を積む
- 言い張り: ルールを曲げて役を作りやすくする

検証で分かった性質: 保留枠は普通の手を速くし（12 巡の和了率 枠 0: 21%、1: 33%、2: 49%、3: 63%）、役満はほとんど速くしない。万能牌は普通の手を約 2 倍、条件の厳しい役を 4〜6 倍にする。

### 4.6. 引き継ぎ（雀士・段位・役の解禁）

ランをまたいで、強さではなく選択肢を増やす。定義は `engine/src/progression.ts`。

雀士（ランの始めの条件が違う）:

雀士の名前は動物のひらがなで、絵（`frontend/public/characters/<id>.svg`）を添える。

| 雀士 | 型 | 始めの条件 | 解禁の条件 |
|---|---|---|---|
| くま | 標準 | 保留3枠・ネクスト2枚、持ち物なし、祝儀4 | 最初から |
| うさぎ | 速攻 | 保留4枠・ネクスト1枚 | 東場を突破する |
| かめ | 門前 | 保留なし・ネクスト4枚・1局の巡数＋3（初段で15巡）、黙聴を持つ | 門前で和了る |
| ぞう | 親番 | 親父の背中を持つ、祝儀2 | 南場を突破する |
| ねこ | 役満 | 保留2枠、化け猫を持つ、祝儀0 | 全場クリアし、役満でも和了る |

雀士の強さの釣り合い（GitHub issue #10）: くま（最初の雀士）はいちばん弱くてよい。ねこはボーナスの雀士として、ほかより強くてよい（その代わり解禁を遅くする）。うさぎ・かめ・ぞうは、型は違っても、上手に打てばはっきりした差が出ないようにする。役満と安手の点差は、麻雀らしさとして点数の式では縮めず、ねこの強みとして残す。

- sim（`npm run sim -w engine -- starts --dans 0,2,4`、組み合わせごとに 100 ラン、ショップでお守りと設備を買う AI）の全場クリア率は、初段・三段・五段の順に、くま 78・62・38%、うさぎ 86・73・57%、かめ 81・70・48%（直す前の三段は 33%）、ぞう 70・57・36%（直す前の三段は 48%）、ねこ 82・72・48%。sim の AI は役満も連荘の損得も考えないので、ねことぞうを弱く見積もる（賢い AI は GitHub issue #13）
- 点数の期待値で打つ AI（`engine/src/ai.ts`。GitHub issue #13。役満・連荘・消耗品・ショップの品も考える）で測り直すと（`starts --dans 0,2,4 --ai smart`、組み合わせごとに 100 ラン）、全場クリア率は初段・三段・五段の順に、くま 98・91・86%、うさぎ 89・85・71%、かめ 99・99・96%、ぞう 93・90・80%、ねこ 96・92・87%。どの雀士も上の AI より大きく上がり、強さの順はかめ＞ねこ≒くま＞ぞう＞うさぎになった。人の感想（ねこ・ぞうが強い）とはまだ合わない。直すかどうかは、β の集計と合わせて決める
- 同じ AI で、ショップで何も買わずにアイテムを 1 つだけ持たせると（`runs --ai smart`、100 ラン、なしで突破した場の平均 3.63）、効き目の大きいものは長考 +0.27・色眼鏡 +0.25・猫に小判 +0.18・千里眼 +0.17・白紙委任 +0.17・化け猫 +0.15・写し（中）+0.13。朱塗り（5筒）と金箔（5筒）は +0.05 で、賢い AI でも小さい（GitHub issue #6）。巡り目（-0.10）と抜き取り（北、-0.17）はなしより悪い
- かめは、保留がないので局の和了率が低く（sim で 5〜6 割。ほかは 8〜9 割）、いちばん弱かった。保留枠を足すと、和了に保留牌を使った手で門前を失って型が崩れるので、ネクストと巡数で補う
- ぞうは、sim では弱め（祝儀 0 では三段の全場クリア 48%）、人の感想では強いとされたので、始めの祝儀を少しだけ足した
- ねこは、sim の AI が役満や万能牌を狙って打たないので強さが数字に出にくいが、人の感想では強い。解禁の条件を厳しくした（α の間なので、前の条件で解禁していた人への手当はしない。dev の解禁の状態はこの変更のときにリセットした）

雀士がはじめから持つお守り（かめの黙聴、ぞうの親父の背中）と設備（ねこの化け猫）は「固有」のもので、売れない。固有のお守りはお守りの枠（5）に数えない（GitHub issue #7）。ランの状態の `charms` には入れず、始めの条件の雀士から求める（`run.ts` の `innateCharms`）。持ち物とショップでは「固有」の印を付け、枠は「お守り 2/5（＋固有 1）」と書く。ショップと福引きには、固有のお守りも持っているものとして並べない。

雀士の解禁は、1 回のランで 1 人まで（GitHub issue #8）。ランを終えたとき、条件を満たしてまだ解禁していない雀士のうち、表の順（うさぎ→かめ→ぞう→ねこ）で最初の 1 人を解禁する。条件は累計の記録（突破した場の最高・和了った役）で見るので、残りの雀士は、次のランを終えたときに 1 人ずつ解禁される。解禁した雀士は解禁の状態に一覧（`characters`）で持つ。一覧を持たない前の記録（端末の `pujan.progress.v1` と、D1 の `progress.characters` が NULL の行）は、読むときに条件を満たしている雀士を全員解禁済みにする（選べていた雀士を選べなくしない）。D1 は、そうして求めた一覧を読んだときに書き戻す。端末は `pujan.progress.v2` に書き、v2 がないときだけ v1 を読む（キャッシュに残った古い画面が v1 に一覧なしで書き戻しても、一覧を失わないため）。ランの準備の画面では、条件を満たして解禁を待っている雀士に「次のランを終えると解禁」と書く。

段位（上がるほど縛りが重なる。全場クリアすると次の段位を選べる）:

| 段位 | 加わる縛り |
|---|---|
| 初段 | なし |
| 二段 | 場の目標点が1.5倍 |
| 三段 | 場を突破したときの祝儀が1少ない（3→2） |
| 四段 | 1局の巡数が1少ない（くまなら11巡） |
| 五段 | 場の目標点が2倍（二段の1.5倍の代わり）。オーラスで和了らないと場を突破できない |
| 雀聖 | ショップの品が2つで、福引きがない（福引き券ももらえない。福引きを足したとき、品の数の縛りを打ち消して全場クリア率が 25% から 43% に上がったため）。オーラスの和了は場の目標点の1/4以上の点数が要る（東 500・南 1,000・西 2,000・北 4,000 点） |

オーラスの和了の縛り（GitHub issue #9）は、親の連荘で何度か和了ったときは、いちばん高い和了で見る。和了の点数は親・本場などを掛けた後の点数。足したときの全場クリア率（組み合わせごとに 100 ラン）:

| AI | 段位 | くま | うさぎ | かめ | ぞう | ねこ |
|---|---|---|---|---|---|---|
| smart | 五段（前→後） | 86→44% | 71→39% | 96→67% | 80→37% | 87→42% |
| smart | 雀聖（前→後） | 88→22% | 78→23% | 96→51% | 81→29% | 86→29% |
| basic | 五段（前→後） | 38→12% | 57→20% | 48→14% | 36→9% | 48→15% |
| basic | 雀聖（前→後） | 25→8% | 42→5% | 46→5% | 24→3% | 37→4% |

どちらの AI でも大きく下がる。局の和了率は 7〜8 割なので、4 つの場のオーラスすべてで和了る条件は重く、目標点の低い東場で負けるランが多くなる。景品だけが効く初段（basic の AI）は、くま 78→75%・うさぎ 86→87%・かめ 81→84%・ぞう 70→73%・ねこ 82→88% で、ほぼ変わらない。人が遊んだ集計を見て、条件の重さを直すかを決める

役の解禁: その役で一度和了ると、その役の巻物がショップに並ぶようになる（はじめは巻物が並ばない）。役に結び付いたお守り（色眼鏡＝混一色、飛び石＝プチ一通、風見鶏＝プチ小四喜、白紙委任＝プチ小三元、青天井＝清一色）も同じ。それ以外のお守り・設備・消耗品・牌の改造は最初から並ぶ。

解禁の状態（和了った役・突破した場の数の最高・全場クリアした最高の段位・解禁した雀士）は、ランキングに載るランではサーバーに、端末だけのランでは端末に記録する。端末は両方を合わせて持つ。ランの始めの条件（雀士・段位・解禁済みの役）は操作ログに入る（§5.3）。

## 5. 技術とアーキテクチャ

### 5.1. 構成

vegtab と同じ npm workspaces のモノレポ。

| パッケージ | 技術 | 内容 |
|---|---|---|
| `engine/` | TypeScript | ルールエンジン。純粋関数、フレームワーク非依存 |
| `frontend/` | Vue 3（Composition API）、Pinia、vite-plugin-pwa | SPA |
| `backend/` | Cloudflare Workers（Hono）、D1 | API。SPA も同じ Worker の Static Assets で配信 |

認証は kan-game.app の ID（ID 基盤が発行する Cookie の JWT を、Worker が公開鍵で検証する）。vegtab の `backend/src/lib/id-*.ts` と `middleware/auth.ts` を手本にする。

### 5.2. エンジン（`engine/`）

| ファイル | 内容 |
|---|---|
| `tiles.ts` | 牌の種類、ドラの求め方 |
| `rng.ts` | シード付き乱数（xorshift32） |
| `hand.ts` | 役判定（5 枚・三対子の 6 枚） |
| `win.ts` | 手元の牌から最も高い和了を探す、待ちを求める（万能牌・ボーナス翻を含む） |
| `score.ts` | 点数表と点数の内訳 |
| `items.ts` | アイテムとボスの定義、局のルール（Modifiers）への反映 |
| `kyoku.ts` | 1 局の状態機械（`startKyoku` と `step`） |
| `run.ts` | ランの進行、局の精算、ショップ |
| `game.ts` | ランと局をまとめた状態、操作（`GameAction`）の適用、操作ログ（`RunLog`）の再生 |
| `week.ts` | ランキングの週（日本時間の月曜で区切る）。サーバーと画面の両方で使う |
| `ai.ts` | 点数の期待値で打つ AI（局・精算・ショップの判断）。sim と、対戦の CPU（§3.7）に使う |
| `sim.ts` | バランス調整用のシミュレーション（確率表、目標の形を狙う AI、ランの到達場）。`index.ts` からは出さない |

原則:

- 状態は書き換えず、新しい状態を返す。乱数の状態も状態に含める
- アイテムの効果は `Modifiers` への差分として書き、効く場所（`win.ts`・`score.ts`・`kyoku.ts`）で読む。アイテムを足すときに本体の分岐を増やさない
- Cloudflare や Vue に依存しない（frontend と backend の両方から使う）

### 5.3. 不正対策

ランの記録は操作ログで送り、サーバーが同じエンジンで再生して点数を確かめる（vegtab の replay-verify と同じ考え方）。エンジンの版が変わると再生結果が変わりうるので、記録に `engine_version` を残す。

操作ログ（`engine/src/game.ts` の `RunLog`）は、エンジンの版（`ENGINE_VERSION`）・シード・始めの条件（雀士・段位・解禁済みの役。ルールと始めの持ち物はここから決まる）・操作（`GameAction`）の列。操作は局の中の操作（打牌・保留・リーチ・和了・配牌の引き直し）、消耗品の使用、祝儀を払う延長、局の精算（親の和了では連荘か和了やめ）、ショップの操作（買う・売る・品替え・福引き・出る）。`replay()` は版の違うログと、途中にできない操作があるログを拒む。同じ操作ログから違う結果になる変更をしたら `ENGINE_VERSION` を上げる。操作の種類を足すだけで、前からある操作だけのログの結果が変わらないとき（消耗品の売却 `sellConsumable`、福引き `gacha`、延長 `extend` など）は上げない。上げると、端末の途中のランとサーバーで記録中のランが版違いで使えなくなるため。

ランキングに載せるランは、次の流れで記録する（`backend/src/lib/runs.ts`）。

1. 画面がランを始めるときに、選んだ雀士と段位を `POST /api/runs` に送る。サーバーは、その ID の解禁の状態で選べるものか確かめ（選べなければ 403）、ランダムなシード・ランの ID・始めの条件を渡す。解禁済みの役はサーバーの記録から入れる。端末がシードを選べると、良い山が出るシードを手元で探してから遊べてしまうため
2. ランが終わったら `POST /api/runs/:id/finish` に操作ログを送る。サーバーは、ログのシードと始めの条件が渡したものと同じこと、版が同じことを確かめ、ログを再生してランが終わっていることを確かめてから、突破した場の数と合計点を書き、解禁の状態を更新する（解禁は減らないので、今の記録と和を取る）。成績は送られてきた値を使わず、再生した結果から出す
3. 同じ ID で新しいランを始めると、終わっていない前のランは記録できなくなる（進めていられるランは 1 つ）。行は、始めて終わらなかったランを数えるために残す（フェーズ 4.5）
4. 記録はランを始めた時刻（サーバーの時刻）の週に入る。送った時刻で決めると、週が変わってから送って記録を載せる週を選べてしまうため

サーバーにつながらずに始めたランと、サーバーの記録ではまだ選べない雀士・段位で始めたラン（端末だけのランで解禁したもの）は、端末の中だけで遊び、ランキングには載せない。送れなかった記録（つながらない、サーバーの一時的な障害）は端末に残し、次に開いたとき、オンラインに戻ったとき、新しいランを始める前に送り直す。送り直せずに残っているあいだに始めたランは、前のランの記録を消さないように端末だけのランにする。

始めたランを捨てて開き直せば、配牌を見てから良いランだけを続けることはできる。手間がかかるので、今は防がない。

再生にかかる時間は 1 ランで 200ms ほど（操作 1 回あたり 1ms 弱）。Workers の有料プランが前提。

### 5.4. ランキングとデータベース（D1）

ランキングは週ごと（日本時間の月曜 0:00 に切り替わる）。各 ID のその週の最高記録を、段位 → 突破した場の数（全場クリアが最上位）→ 4 場の合計点（突破できなかった最後の場の点数を含む）の順に並べる。同じ成績は同じ順位。雀士は区別せず、表示だけする。名前と公開への同意がある ID だけを載せ、上位 100 人と本人の記録を返す（`GET /api/rankings/weekly`）。

名前は kan-game.app 全体で 1 つ（kan/game docs/ID_DESIGN.md「名前」）。ランキングの画面で名前を登録し、プチ麻雀での公開に同意する。ほかのゲームで名前を登録済みなら、同意だけを求める。

表は `backend/migrations/0002_ranked_runs.sql`（`0001_runs.sql` はデイリーを前提にした叩き台で、0002 が作り直す）と `0004_progression.sql`（始めの条件・段位・解禁の状態）、`0005_feedback_and_play_logs.sql`（感想と操作ログ。フェーズ 4.5）。

| 表 | 内容 |
|---|---|
| `runs` | サーバーがシードを渡したラン（始めの条件を含む）。終わったら成績と操作ログを書く（操作ログはプレイの集計に使う） |
| `weekly_best` | 週ごとの各 ID の最高記録（段位と雀士を含む） |
| `profiles` | ランキングに出す名前と、公開への同意 |
| `progress` | 各 ID の解禁の状態（§4.6） |
| `feedback` | 遊んだ人の感想と、送ったときのランの様子（`POST /api/feedback`。1 つの ID につき 1 時間に 5 件まで） |
| `deleted_accounts` | 退会した ID（Cookie は退会後も最長 400 日有効なので、以後の書き込みを断るために残す） |

退会では ID 基盤が `GameService.deleteAccount` を呼び、その ID の記録をすべて消す（`backend/src/game-service.ts`）。
