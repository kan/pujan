# SPEC.md — プチ麻雀（pujan）仕様書

ゲームルール・ローグライト・画面・API・データ構造の正本。ルールに関わる変更の前に該当する節を読み、変更したらこの文書も直す。

ルールとローグライトの数値は、プロトタイプ [`docs/prototype/puchi-mahjong.html`](prototype/puchi-mahjong.html) で検証して確定したもの。迷ったらプロトタイプの挙動を正とし、食い違いを見つけたらこの文書かエンジンのどちらが正しいかを利用者に確かめる。

## 1. プロジェクト概要

### 1.1. コンセプト

手牌を 5 枚（雀頭 2 ＋面子 3）に縮めた麻雀を、Balatro 型のローグライトとして遊ぶ Web ゲーム。

- スマートフォンの縦持ちで、牌を大きく表示できる
- 1 局が 30 秒〜1 分と短く、スキマ時間で遊べる
- 麻雀を知らない人にもルールが伝わりやすい

着想は「白發中が 3 枚あれば大三元と言い張れる」こと。役を 5 枚に縮めた「プチ役」の名前の格好よさと、「それは無理がある」という笑いの両方をテーマにする。

### 1.2. 配信と名前

- 名前: プチ麻雀。リポジトリ・パッケージ名は `pujan`
- kan-game.app のゲームの 1 つとして Web（PWA）で配信する。本番 `https://pujan.kan-game.app`、開発 `https://pujan-dev.kan-game.app`（予定）
- ID・名前・退会は kan-game.app の ID 基盤（kan/game）と共通（§5.1）

### 1.3. モード

| モード | 状態 | 内容 |
|---|---|---|
| ローグライト | 最初に作る | ソロ。東南西北の 4 場を勝ち抜く（§4） |
| AI 対戦 | 後で作る | CPU と 1 対 1（§3.7） |
| ネット対戦 | 後で作る | プレイヤー同士の 1 対 1（§3.7） |

3 つとも同じエンジン（`engine/`）の上に作る。

## 2. 画面と世界観

### 2.1. 世界観

麻雀卓の緑のラシャと象牙色の牌。色と書体はプロトタイプの `:root` を基準にする（`frontend/src/theme.css` に写してある）。

- 牌の地は象牙色（CSS で描く）。面の絵は公開素材 [FluffyStuff/riichi-mahjong-tiles](https://github.com/FluffyStuff/riichi-mahjong-tiles)（CC0）の SVG を使う（`frontend/public/tiles/`。出典とライセンスは同じフォルダの `README.md`）。プロトタイプは CSS と文字で描いていた
- 萬子・筒子・索子・字牌は素材の絵柄のまま。白は無地（絵柄のない牌）
- 赤の 5 は素材の赤牌の絵を使う。朱塗りで 5 以外の牌が赤牌になったときは、素材に赤版がないので左上に赤い印を付ける
- 金牌は金色の地にする。万能牌は右上に金色の「J」を付ける

### 2.2. 局の画面（縦持ち 1 画面）

上から次の順に並べる。プロトタイプの最終版（UI を確定した版）と同じ。

1. **ヘッダー**: タイトル、役（役と遊び方をすぐ開く）、メニュー
2. **状況の帯**: 4 局の並び（親とボスの印つき）、局名と本場、巡（残り 3 巡以下で金、最終巡で赤）、点数／目標と進捗バー
3. **情報**: リーチ中の印、ボスの縛り、ドラ表示→ドラ（または万能牌）、自風（いずれも牌の絵で大きく）
4. **持ち物**: 祝儀、お守りの数（タップで持ち物一覧）、消耗品（タップで使う）
5. **河**: 1 行の細い帯。新しい捨て牌が右端。タップで全部を広げる
6. **中央**: その時に要る情報だけ。和了れるときは役と点数を金の枠で大きく。それ以外は待ち牌と残り枚数、操作のヒント
7. **保留枠とネクスト**: 保留枠（左）と、次にツモる牌（右。左が次、`←` で順番を示す）
8. **手牌**: 手牌 4 枚とツモ牌
9. **操作ボタン**: その場でできるものだけ出す（配牌の引き直し、保留、リーチ、和了）

操作:

- 牌をタップで選択、選んだ牌をもう一度タップで捨てる（「捨てる」ボタンは置かない）
- 空いた保留枠をタップすると、選んだ牌を保留する
- 和了れるときは、和了に使う 5 枚（三対子は 6 枚）を金の枠で示す

### 2.3. その他の画面

- 和了: 和了牌、役と翻、点数の内訳（親・リーチ後の巡・本場・役レベルなど）、祝儀。親の和了では「和了やめ」「連荘する」
- 流局: 聴牌料・罰符・リーチ棒の没収
- 場の開始: 目標点、親番の局、オーラスのボス
- 場の突破: 局ごとの記録と祝儀の内訳
- ショップ: 品物 3 つ、品替え、持っているお守りの売却
- 牌の改造の対象選び: 34 種の牌と、山にある枚数・赤・金
- ラン終了・全場クリア（ランキングへの記録の様子）
- メニュー（TAKO-SEN に倣う）: ランキングの名前、kan-game.app のアカウント（ポータルへのリンク）、今週のランキング、遊び方（チュートリアル）、役と遊び方、持ち物、新しいランを始める（確認つき）、プチ麻雀について（素材と書体のライセンス）
- 役と遊び方: タブで、遊び方・ボーナスの翻・1〜2翻・3翻以上・役満・点数表・アイテムに分ける。組み合わせの役は牌の絵で例を示す（例の手は `frontend/src/lib/help.ts`。その役になることをテストで確かめる）
- チュートリアル（TAKO-SEN に倣う）: 山の並びを決めた練習の局で、捨てる・保留する・ネクストを見る・和了るを実際に操作してもらい、言われた操作ができたら次へ進む。次に押すところ（牌・空き枠・ボタン）は、文字の指示に加えて金の輪と指のマークで光らせる（動きを減らす設定では動かない輪だけ）。そのあとランの流れ（場・目標点・親・ボス・ショップ・祝儀）を説明する。初めて開いたときは見るかどうかを聞く（`frontend/src/lib/tutorial.ts`）
- ランキング（§5.4）

ルール設定の画面は置かない（プロトタイプの設定画面はルールの調整用だった）。ルールはいつも既定（12巡・保留3枠・ネクスト2枚・赤牌あり・海底あり）。

## 3. ゲームルール

### 3.1. 牌と山

- 通常の 136 枚（34 種×4 枚）。ローグライトでは牌の改造で種類ごとの枚数が 0〜5 枚に変わる（§4.5）
- 赤牌: 各色の 5 に 1 枚ずつ（設定で外せる）
- 金牌: 牌の改造「金箔」で作る。和了に使うと祝儀＋2
- 局ごとに山を作り直す（和了ったあとも、流局のあとも）

### 3.2. 局の流れ

- 配牌は 4 枚。1 巡に 1 枚ツモり、手牌・ツモ牌・保留牌から 5 枚で和了判定する
- 1 局は 12 巡。和了るか、12 巡を終えると局が終わる。**1 局で和了れるのは 1 回**
- 打牌: 手牌・ツモ牌・保留牌のどれでも捨てられる。保留牌を捨てると、空いた枠にツモ牌が入る
- **保留枠**: 3 枠。牌を置いておけ、和了判定に使える。手牌と保留枠の入れ替えはない（どちらも和了判定に使うため）
- **ネクスト**: 次にツモる 2 枚が見える
- **配牌の引き直し**: 1 局に 1 回、1 巡目でまだ何も捨てても保留してもいないときだけ。手牌とツモ牌を山に戻して配り直す
- **聴牌料**: 流局時、最後の打牌のあとに聴牌していれば 200 点
- **リーチ**: 牌を選び、それを捨てると聴牌になるときに宣言できる。リーチ棒 100 点（流局すると没収、和了ると戻る）。以後は手牌も保留も固定でツモ切りのみ、ネクストが隠れる。和了で 1 翻と裏ドラ。一発はなく、代わりに宣言から和了までの巡数×100 点
- **ドラ**: ドラ表示の次の牌が 1 枚 1 翻。設備で万能牌に変えられる（§4.4）
- **海底**: 最終巡のツモで和了ると 1 翻（設定で外せる）
- **親**: 4 局のうち 1 局が親番（場の開始時に分かる）。親の和了は 1.5 倍で、和了後に「連荘（本場が積まれる）」か「和了やめ」を選ぶ。本場は次の和了に 1 本場 100 点。流局すると親は流れる（聴牌でも連荘しない）。親のノーテン流局は罰符 300 点×（本場数＋1）
- **自風**: 親の局は東（場風と重なればダブ東）。それ以外は親の局から逆算し、親の直前が南、その前が西、親の直後が北

不採用にしたもの（再検討するときの参考）:

- 2 枚ツモって 1 枚選ぶ: 和了率は最も上がった（12 巡で 76%）が、麻雀経験者ほど混乱する
- 和了ったあとも 12 巡まで続ける Balatro 式: 安手の連打が最適解になり、麻雀らしくない
- 聴牌連荘: 聴牌が容易なので親番が終わらなくなる
- 一発: ネクストがあるのでリーチがやり得になる

### 3.3. 役

和了形は対子＋面子（順子・刻子）が基本。役がなくても和了れる（役なし 100 点）。

| 役 | 条件 | 翻 |
|---|---|---|
| プチ国士 | 三元牌・風牌・1 牌・9 牌を 1 枚ずつ＋そのどれかの対子 | 1 |
| 断么九 | 么九牌を含まない | 1 |
| 役牌 | 三元牌・場風・自風の対子か刻子＋面子。重なれば加算（親の東はダブ東で 2） | 1〜 |
| 門前 | 保留牌を使わずに和了（役満以外と複合） | 1 |
| 混一色 | 数牌 1 色＋字牌 | 2 |
| プチ三色 | 同じ数字の 3 色の面子＋対子 | 2 |
| プチ一通 | 同色の 5 連（12345 など）。清一色と必ず複合 | 2 |
| プチ小四喜 | 風牌 3 種＋対子（何でも可） | 2 |
| 三対子 | 保留を含めた 6 枚で対子 3 組（門前とは両立しない） | 2 |
| 清一色 | 数牌 1 色のみ | 3 |
| プチ四暗刻 | 刻子＋対子 | 3 |
| プチ小三元 | 白發中＋対子 | 5 |
| 混老頭 | 么九牌のみで刻子を含む | 役満 |
| 字一色 | 字牌のみ | 役満 |
| 緑一色 | 2・3・4・6・8 索と發のみ | 役満 |
| プチ大四喜 | 東南西北＋三元牌 1 枚 | 役満 |
| プチ槓 | 同じ牌 4 枚＋何か 1 枚 | 役満 |
| 天和 | 1 巡目のツモで和了 | 役満 |
| 地和 | 一度も捨てずに 2 巡目で和了（保留は可） | 役満 |
| プチ大三元 | 三元牌の刻子＋残りの三元牌 1 枚ずつ | ダブル役満 |

ボーナスの翻: リーチ 1、海底 1、ドラ 1／枚、赤 1／枚、裏ドラ 1／枚。ボーナスは役に数えない（ボス「1 翻縛り」で効く）。

役満は重なれば倍数を足す（例: プチ大三元＋字一色は 3 倍役満）。147・258・369 は役にならない（お守り「飛び石」で順子になる）。

難しさの目安（配牌 5 枚で完成する確率／保留なし 12 巡での和了率）は、コンセプト資料とエンジンのシミュレーションで確かめる。主なもの: 基本和了 1/1,281・21%、プチ国士 1/2,170・25%、清一色 1/6,249・12%、プチ小三元 1/29,756・2.4%、プチ大三元 1/1,874,652・0.2%。

配牌の確率は「形」の確率で、上位の役（役満など）に吸収される手も数える。基本和了は対子＋順子か刻子、清一色は 1 色の対子＋面子（プチ一通の 5 連は含まない）。配牌の確率はエンジンの数え上げ（`engine/src/sim.ts` の `dealTable`）と一致し、回帰テストにしている。12 巡の和了率は AI の打ち方で変わる（エンジンの AI では、ネクストを使わないときに基本和了 18%・プチ国士 25%・清一色 12%）。

### 3.4. 点数

| 翻 | 名前 | 点数 |
|---|---|---|
| 0（役なし） | — | 100 |
| 1〜4 | — | 200・400・800・1,600（100×2^翻） |
| 5 | 満貫 | 2,000 |
| 6〜7 | 跳満 | 3,000 |
| 8〜10 | 倍満 | 4,000 |
| 11〜12 | 三倍満 | 6,000 |
| 13〜 | 数え役満 | 8,000 |
| 役満 | — | 8,000×倍数 |

お守り「青天井」があると上限がなくなり、翻ごとに倍のまま。

基本点に次の順で掛け合わせる・足す（`engine/src/score.ts`）: 役レベル（×1.5^Lv）→ 安手の美学（役なし×4）→ 親（×1.5、100 点単位に切り上げ）→ リーチ後の巡（＋100／巡）→ 本場（＋100／本場）。

### 3.5. 局の精算

- 和了: 点数を加える
- 流局: 聴牌料（聴牌時）を加え、親のノーテン罰符とリーチ棒を引く

### 3.6. 決定性

山の並びとショップの品揃えはシードから決まる。同じシードと同じ操作列からは必ず同じ結果になる（サーバーでの操作ログの再生による検証のため。§5.3）。乱数は xorshift32（vegtab と同じ）。

全員で同じシードを遊ぶ形（デイリーなど）は設けない。ランはいつもランダムなシードで遊び、競い合いの中心は将来の対戦モード（§3.7）とする。ランキングに載せるランのシードはサーバーが渡す（§5.3）。

### 3.7. 対戦モード（後で作る）

検討済みの方針。作るときに詳細を詰める。

- 1 対 1。1 翻縛り（役なしの最速和了が最適解になるのを防ぐ）
- 鳴きなし（ポンすると残りが単騎待ちになり極端なため）。ロンとツモのみ
- 保留枠は表向きに公開する
- 相手が保留枠に置いた牌でもロンできる（槍槓と同じ扱い。置いた瞬間だけ）。常時ロン可にする案もあり、設定で切り替えて比較する
- AI 対戦の CPU はエンジンを使う。ネット対戦は Durable Objects で部屋を持つ

## 4. ローグライト

### 4.1. ランの流れ

- 東南西北の 4 場を勝ち抜けばクリア。1 場は 4 局
- 場の目標: 東 1,000・南 2,000・西 4,000・北 8,000 点。点数は場ごとにリセット、場風も変わる
- 場の開始時に、親番の局（ランダム）とオーラス（4 局目）のボス（ランダム）を示す
- 局が終わるたびにショップが開く（4 局目のあとは場の判定）
- 4 局の合計が目標に届かなければラン終了

### 4.2. ボス（オーラスの縛り）

| ボス | 縛り |
|---|---|
| 保留封印 | 保留枠が使えない |
| 霧 | ネクストが見えない |
| 1 翻縛り | 役なしでは和了れない（ドラ・赤・門前は役に数えない） |
| 早仕舞い | 巡数が 4 少ない |
| 質素倹約 | ドラと赤の翻がつかない |

### 4.3. 祝儀（お金）

点数とは別の通貨。最初は 4。

- 和了: 2＋翻数の半分（最大 6）。役満は 6。金牌 1 枚につき＋2
- 流局時の聴牌: 1
- 場の突破: 3＋利子（5 ごとに 1、最大 5）＋目標超過（50% ごとに 1、最大 3）

### 4.4. アイテム

| 種類 | 枠 | 価格 | 内容 |
|---|---|---|---|
| お守り | 5 | 5（青天井は 8） | 常時効果。売ると祝儀 2 |
| 設備 | — | 8 | 永続の強化 |
| 消耗品 | 2 | 3 | 局の中で 1 回使う |
| 牌の改造 | — | 3 | 山の構成を変える。ラン中ずっと残る |
| 役の巻物 | — | 3 | 指定の役を含む和了の点数×1.5（重ねがけ可） |

ショップは 3 品。種類の出やすさはお守り 40%・消耗品 20%・牌の改造 15%・役の巻物 15%・設備 10%。持っているお守りと設備、並んでいる品は重ならない。品替えは祝儀 2。

**お守り**

| お守り | 軸 | 効果 |
|---|---|---|
| 早指し | 速攻 | 6 巡以内の和了で＋1 翻 |
| 安手の美学 | 速攻 | 役なしの和了が 4 倍 |
| 黙聴 | 門前 | 門前が 2 翻 |
| 一発屋 | リーチ | リーチの次のツモで和了ると＋2 翻 |
| 博打打ち | リーチ | リーチの巡数ボーナス 2 倍、リーチ棒 300 点 |
| 裏の顔 | リーチ | 裏ドラ表示が 2 枚 |
| 親父の背中 | 親番 | 親の倍率が 2 倍 |
| 居座り | 親番 | 本場ボーナス 3 倍 |
| 赤い糸 | 赤ドラ | 赤牌が 1 枚 2 翻 |
| 色眼鏡 | 言い張り | 萬子と索子を同じ色として扱う |
| 飛び石 | 言い張り | 147・258・369 を順子として扱う |
| 風見鶏 | 言い張り | すべての風牌が役牌 |

**設備**

| 設備 | 効果 |
|---|---|
| 物置 | 保留枠＋1 |
| 千里眼 | ネクスト＋1 |
| 長考 | 1 局の巡数＋2 |
| 招き猫 | ドラ表示が 2 枚 |
| 化け猫 | ドラ牌が万能牌になる（ドラの翻はなくなる） |
| 猫に小判 | 万能牌として使ってもドラの翻が残る（化け猫が必要） |

**消耗品**: ツモ直し（今のツモ牌を山の底へ戻して引き直す）、河拾い（最後に捨てた牌をツモ牌として拾う）、山覗き（この局の間、山の先 5 枚まで見える）、総入れ替え（手牌とツモ牌を山に戻して配り直す。巡は進まない）。リーチ中は使えない。

**牌の改造**: 朱塗り（選んだ牌の 2 枚を赤牌に）、金箔（1 枚を金牌に）、抜き取り（その牌を山から全部抜く）、写し（その牌を 5 枚に）。

### 4.5. ビルドの軸

アイテムは次の軸のどれかを伸ばすように作る。新しいアイテムもこの軸に沿わせ、軸を増やすときは仕様を更新する。

- 速攻: 保留・ネクストで安く早く和了る
- 門前・リーチ: 保留を使わず、ネクストを捨てて翻を稼ぐ
- 役満: 牌山の改造と万能牌で一発を狙う
- 親番: 連荘で局数を稼ぐ
- 赤・ドラ: ボーナスの翻を積む
- 言い張り: ルールを曲げて役を作りやすくする

検証で分かった性質: 保留枠は普通の手を速くし（12 巡の和了率 枠 0: 21%、1: 33%、2: 49%、3: 63%）、役満はほとんど速くしない。万能牌は普通の手を約 2 倍、条件の厳しい役を 4〜6 倍にする。

### 4.6. 本実装で足すもの

- 引き継ぎ（強さではなく選択肢を増やす）: 初めて和了った役の解禁、初期条件の違う雀士、難易度の段位（初段〜雀聖）
- やり込み: 高段位でのクリア、役満全種の和了、エンドレス
- 週ごとのランキング（フェーズ 3 で作った。§5.4）

## 5. 技術とアーキテクチャ

### 5.1. 構成

vegtab と同じ npm workspaces のモノレポ。

| パッケージ | 技術 | 内容 |
|---|---|---|
| `engine/` | TypeScript | ルールエンジン。純粋関数、フレームワーク非依存 |
| `frontend/` | Vue 3（Composition API）、Pinia、vite-plugin-pwa | SPA |
| `backend/` | Cloudflare Workers（Hono）、D1 | API。SPA も同じ Worker の Static Assets で配信 |

認証は kan-game.app の ID（ID 基盤が発行する Cookie の JWT を、Worker が公開鍵で検証する）。vegtab の `backend/src/lib/id-*.ts` と `middleware/auth.ts` を手本にする。

### 5.2. エンジン（`engine/`）

| ファイル | 内容 |
|---|---|
| `tiles.ts` | 牌の種類、ドラの求め方 |
| `rng.ts` | シード付き乱数（xorshift32） |
| `hand.ts` | 役判定（5 枚・三対子の 6 枚） |
| `win.ts` | 手元の牌から最も高い和了を探す、待ちを求める（万能牌・ボーナス翻を含む） |
| `score.ts` | 点数表と点数の内訳 |
| `items.ts` | アイテムとボスの定義、局のルール（Modifiers）への反映 |
| `kyoku.ts` | 1 局の状態機械（`startKyoku` と `step`） |
| `run.ts` | ランの進行、局の精算、ショップ |
| `game.ts` | ランと局をまとめた状態、操作（`GameAction`）の適用、操作ログ（`RunLog`）の再生 |
| `week.ts` | ランキングの週（日本時間の月曜で区切る）。サーバーと画面の両方で使う |
| `sim.ts` | バランス調整用のシミュレーション（確率表、目標の形を狙う AI、ランの到達場）。`index.ts` からは出さない |

原則:

- 状態は書き換えず、新しい状態を返す。乱数の状態も状態に含める
- アイテムの効果は `Modifiers` への差分として書き、効く場所（`win.ts`・`score.ts`・`kyoku.ts`）で読む。アイテムを足すときに本体の分岐を増やさない
- Cloudflare や Vue に依存しない（frontend と backend の両方から使う）

### 5.3. 不正対策

ランの記録は操作ログで送り、サーバーが同じエンジンで再生して点数を確かめる（vegtab の replay-verify と同じ考え方）。エンジンの版が変わると再生結果が変わりうるので、記録に `engine_version` を残す。

操作ログ（`engine/src/game.ts` の `RunLog`）は、エンジンの版（`ENGINE_VERSION`）・シード・基本ルール・操作（`GameAction`）の列。操作は局の中の操作（打牌・保留・リーチ・和了・配牌の引き直し）、消耗品の使用、局の精算（親の和了では連荘か和了やめ）、ショップの操作（買う・売る・品替え・出る）。`replay()` は版の違うログと、途中にできない操作があるログを拒む。同じ操作ログから違う結果になる変更をしたら `ENGINE_VERSION` を上げる。

ランキングに載せるランは、次の流れで記録する（`backend/src/lib/runs.ts`）。

1. 画面がランを始めるときに `POST /api/runs` を呼び、サーバーがランダムなシードとランの ID を渡す。端末がシードを選べると、良い山が出るシードを手元で探してから遊べてしまうため
2. ランが終わったら `POST /api/runs/:id/finish` に操作ログを送る。サーバーは、ログのシードが渡したシードと同じこと、基本ルールが既定のルールであること、版が同じことを確かめ、ログを再生してランが終わっていることを確かめてから、突破した場の数と合計点を書く。成績は送られてきた値を使わず、再生した結果から出す
3. 同じ ID で新しいランを始めると、終わっていない前のランは消え、記録できなくなる（進めていられるランは 1 つ）
4. 記録はランを始めた時刻（サーバーの時刻）の週に入る。送った時刻で決めると、週が変わってから送って記録を載せる週を選べてしまうため

サーバーにつながらずに始めたランは端末の中だけで遊び、ランキングには載せない。サーバーは基本ルールが既定であることも確かめる（画面にはルールを変える手段がないが、ログは信頼できない入力なので）。送れなかった記録（つながらない、サーバーの一時的な障害）は端末に残し、次に開いたとき、オンラインに戻ったとき、新しいランを始める前に送り直す。送り直せずに残っているあいだに始めたランは、前のランの記録を消さないように端末だけのランにする。

始めたランを捨てて開き直せば、配牌を見てから良いランだけを続けることはできる。手間がかかるので、今は防がない。

再生にかかる時間は 1 ランで 200ms ほど（操作 1 回あたり 1ms 弱）。Workers の有料プランが前提。

### 5.4. ランキングとデータベース（D1）

ランキングは週ごと（日本時間の月曜 0:00 に切り替わる）。各 ID のその週の最高記録を、突破した場の数（全場クリアが最上位）→ 4 場の合計点（突破できなかった最後の場の点数を含む）の順に並べる。同じ成績は同じ順位。名前と公開への同意がある ID だけを載せ、上位 100 人と本人の記録を返す（`GET /api/rankings/weekly`）。

名前は kan-game.app 全体で 1 つ（kan/game docs/ID_DESIGN.md「名前」）。ランキングの画面で名前を登録し、プチ麻雀での公開に同意する。ほかのゲームで名前を登録済みなら、同意だけを求める。

表は `backend/migrations/0002_ranked_runs.sql`（`0001_runs.sql` はデイリーを前提にした叩き台で、0002 が作り直す）。

| 表 | 内容 |
|---|---|
| `runs` | サーバーがシードを渡したラン。終わったら成績を書く |
| `weekly_best` | 週ごとの各 ID の最高記録 |
| `profiles` | ランキングに出す名前と、公開への同意 |
| `deleted_accounts` | 退会した ID（Cookie は退会後も最長 400 日有効なので、以後の書き込みを断るために残す） |

退会では ID 基盤が `GameService.deleteAccount` を呼び、その ID の記録をすべて消す（`backend/src/game-service.ts`）。
